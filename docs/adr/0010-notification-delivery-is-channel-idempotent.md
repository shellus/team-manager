# 通知投递按渠道冻结目标并幂等重试

## 状态

已接受并实施，2026-08-25。

## 背景

一个通知策略可以同时启用通用 Webhook、飞书、企业微信和 Telegram。旧实现把一次投递视为一个整体：任一后置渠道失败后，重试会再次调用已经成功的前置渠道；同时仅检查 HTTP 状态，无法识别企业微信、飞书或 Telegram 在 HTTP 200 响应中返回的业务错误。策略在重试期间被修改时，在途通知还会切换目标。

这些行为会造成重复提醒、虚假成功和不可解释的投递目标变化，尤其不适合到期和自动移除失败告警。

## 决策

- 通知入队时把当前渠道配置冻结到 `notification_deliveries.configuration_snapshot`。
- 每个渠道业务成功后立即写入 `delivered_channels`；后续尝试跳过这些渠道，只处理尚未成功的渠道。
- 一次通知总计最多尝试 3 次，不因每日调度重新创建后续重试；达到上限后进入 `exhausted`。
- 通用 Webhook 以成功 HTTP 状态为准。飞书、企业微信和 Telegram 还必须解析响应体并确认各自业务成功码。
- 投递历史只暴露渠道名称、已成功渠道和待发送渠道，不暴露冻结的 URL、Token 或 Chat ID。
- 旧投递没有配置快照时才回退到当前策略配置，作为迁移兼容路径。
- 通知策略只按业务事件建模；迁移后停用以 `wecom`、`feishu` 等渠道名创建的旧策略，但保留其历史投递记录。

## 后果

多渠道投递可以部分完成且不会重复打扰已经成功的渠道；运营人员能够从投递历史判断剩余故障范围。在途投递保持入队时的目标，即使管理员随后修改策略，新配置也只影响新通知。数据库会保留渠道目标快照，其中可能包含 Webhook URL 或 Bot Token，因此该字段不得通过普通 API 返回，数据库备份继续按秘密数据保护。
