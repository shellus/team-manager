# 账号代理路由一致性问题

状态：待处理。本文只记录问题与后续决策范围，尚未选择方案，也未修改业务代码或运行配置。

## 问题结论

当前系统把三个不同层次的代理事实放在同一条请求链路中，但界面只提供一个名为“换 IP”的 GAM 代理入口：

1. Team Manager 在 `account_operational_profiles` 中保存账号级 HTTP 代理地址，供 ChatGPT HTTP 请求使用；
2. GAM 保存住宅代理的 SID、国家、ASN、州/省和城市，并向 Team Manager 提供账号稳定 HTTP 代理地址；
3. curl-cffi worker 可以配置全局默认代理，在单次请求没有账号代理时作为最终回退。

GAM 返回的账号 HTTP 代理地址是稳定入口。GAM 轮换上游 SID 或地区后，该入口不变并自动跟随新出口，因此 GAM 代理配置与 Team Manager 保存的地址是同一条账号路由的控制层和连接层，不是两份需要同步编辑的住宅代理配置。

## 当前行为

### 新建账号未填写代理

- 账号级 HTTP 代理保持为空。
- 账号已绑定 GAM 时，部分业务会从 GAM 取得稳定 HTTP 代理地址并保存到 Team Manager。
- 账号未绑定 GAM 时，无法从 GAM 补齐账号代理。
- 请求进入 curl-cffi worker 时，如果仍没有账号代理且部署配置了全局默认代理，请求会静默使用全局代理；未配置全局代理时才会直连。
- 因此，多个未配置账号代理的账号可能共用同一个全局代理出口，而不是获得账号独立出口。

### 页面代理操作

- 账号列表和详情中的“换 IP”只编辑 GAM 的结构化住宅代理配置。
- 未绑定 GAM 的账号无法打开该入口。
- 手工新建账号时可以填写任意账号 HTTP 代理地址。
- 后端账号更新接口也支持修改或清除账号 HTTP 代理，但现有账号编辑界面不展示该字段。

### 不一致的业务边界

常规 ChatGPT 查询、刷新和部分 Workspace、凭证请求允许请求在缺少账号代理时进入 worker，并由全局代理兜底。绑定支付方式则要求账号级代理或 GAM 提供的账号代理，二者都不存在时直接失败，不使用全局兜底。

这使“账号未配置代理”的结果取决于具体业务入口：部分请求共享全局出口，部分请求拒绝执行。

## 影响

- “换 IP”这一名称没有说明它只控制 GAM 住宅代理，容易被理解为账号所有上游请求的统一代理设置。
- 未绑定 GAM 的现有账号缺少可见的账号 HTTP 代理维护入口。
- 全局代理回退是隐式行为，页面无法判断当前账号正在使用账号代理、GAM 稳定代理、全局代理还是直连。
- 不同业务对缺少账号代理的处理不一致，可能在普通刷新成功后，到支付写操作阶段才暴露代理缺失。
- 如果运营目标要求账号级出口隔离，静默共享全局代理不满足该目标。

## 后续需要裁决

1. 明确账号代理的统一优先级和缺失策略：账号级代理、GAM 稳定代理、全局代理、直连分别在什么场景允许使用。
2. 决定全局代理是正式共享兜底、仅限诊断的部署兜底，还是应在账号业务中禁止静默使用。
3. 决定页面是分别提供“账号 HTTP 代理”和“GAM 住宅代理”，还是用一个入口明确展示代理来源并按来源提供对应操作。
4. 统一普通请求、Workspace、凭证、Token 刷新和支付写操作对代理缺失的处理。
5. 确定是否需要在账号详情中展示有效代理来源和隔离状态；展示不得下发代理密码等连接凭据。

## 后续验收范围

- 覆盖未绑定 GAM、已绑定 GAM、手工代理、全局代理和完全无代理的组合测试。
- 明确验证新建账号未填写代理时的实际路由，不把请求成功等同于账号已获得独立代理。
- 验证修改 GAM SID 或地区后，浏览器操作与 Team Manager HTTP 请求使用同一新出口。
- 验证现有账号可以按最终裁决维护账号 HTTP 代理，并能区分该操作与 GAM 住宅代理轮换。
- 验证支付写操作与其他 ChatGPT 请求遵循同一份代理缺失策略，或在文档和界面中明确说明有意存在的差异。
